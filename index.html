AccountsAgent toolkit

Your CRM,layer by layer.

A CRM is where your team keeps customer records and notes. Each layer has a job, from signing staff in to showing them a customer’s details.

Set up the three services below for your coding agent. Once your accounts are ready, give your agent this page’s URL and ask it to read the instructions for your coding agent.

Your agent’s toolkit

Ask your agent to use these tools. You don’t need separate accounts for them.

  • Node.js

    Runs the tools your agent uses to build the CRM.

  • npm

    Downloads and manages the ready-made pieces of code your CRM uses.

  • TypeScript

    The language your agent writes in. It helps catch mistakes early.

  • React

    Builds the screens your team uses to find customers and add notes.

  • Vite

    Lets your agent preview the CRM and prepare it for publishing.

  • TanStack Router

    Connects the screens, so clicking a customer’s name opens their record.

  • shadcn/ui

    Provides ready-made buttons, menus and forms for the CRM.

  • Tailwind CSS

    Controls how the screens look, including colours, spacing and layout.

  • Zod

    Checks that information is in the format the CRM expects, such as a valid email address before saving a customer.

  • Vitest + React Testing Library

    Check individual features. If someone tries to save an empty note, does the form explain what they need to enter?

  • Playwright

    Tests a whole task in a browser. Can a staff member sign in, find a customer, add a note and still see it after refreshing?

Instructions for your coding agent

Help the user take their app from idea to a working deployment. Use the services and tools on this page as your starting point. Take the lead on technical decisions and explain them in plain English. Ask the user how they work, what they need, and what they call things.

  1. Set up the project

    Check whether the user already has an app or a GitHub repository. If they do, inspect it first. If they’re starting fresh, create a GitHub repository for their app. For an internal tool, recommend keeping the repository private.

    Check which services you can already access. When the user needs to create an account, connect a service, install a plugin or skill, or approve access, give them one specific action at a time. Explain why it’s needed and verify the connection afterwards. Use the service’s sign-in or permissions flow. Keep passwords and secret keys out of chat and the repository.

  2. Agree on the brief

    Ask a few focused questions at a time. Find out who will use the app, what they need to do, what information they need, and which features matter for the first version. Ask them to walk you through one typical task from start to finish. Use their own vocabulary for people, records and actions.

    Write BRIEF.md with the purpose, users, concepts, agreed features and what a successful first version looks like. Summarise it in chat so the user can correct it. Get their agreement before moving on.

  3. Choose and document the stack

    Use the services and tools on this page wherever they fit the agreed brief. Explain which ones you’ll use and what each will do for this app. For example, Zod can check customer details before they’re saved.

    If the existing app uses a different stack, the user has requested another tool, or the brief gives you a reason to change something, explain the choice before making the change. Describe the tradeoffs, including any rework, cost or ongoing effort that matters. Give a recommendation and let the user decide. Record the agreed choices and reasons in TECH_STACK.md.

  4. Write the implementation plan

    Take the lead and write IMPLEMENTATION_PLAN.md. Break the work into manageable phases. For each phase, explain what the user will be able to do when it’s finished and how you’ll test it. Plan for the user to review each phase in their browser at a staging URL. Include a release step after their final approval, and give them a short summary in chat.

  5. Build and test on staging

    Once the three documents are in place and reflect the agreed direction, create a staging branch and publish it to a stable staging URL. Configure updates to that branch to deploy there. Give staging its own database, sign-in settings and credentials. Keep it behind staff login and label it clearly as staging.

    Explain staging to the user in plain English: “This is your sandbox. Open this link to try the app with fictional customers. You can add or edit records here without affecting real customers. This is where you’ll review and approve changes before they go live.” Create the user’s staging app account, send a sign-in invitation for that environment, and confirm they can get in. They should be able to review everything in a browser without installing development tools or running commands.

    Create and document scripts for setting up an empty database, applying versioned migrations, loading fictional demo records, and resetting and reseeding staging. Make seeding repeatable without duplicating records. Keep the user’s staging login working after a reset. Have demo and reset scripts target staging by default and refuse to run against live in normal use. On live, apply the reviewed migrations and any setup data the app needs to work.

    Build light and dark themes that automatically follow the device’s system theme.

    Use Vitest and React Testing Library to check individual features. Use Playwright to test the main tasks from the brief in a browser. Run the relevant tests after each phase.

    Use test accounts and fictional customer records in a separate test environment. For a private CRM, verify that approved staff can complete their work and that the database denies access to customer records when someone is signed out. Test the main task at phone and desktop sizes and verify that the app follows changes to the system theme.

    After each phase, share the staging link and a short task the user can try. Before release, run the full suite, fix failures, and tell the user what passed and anything you couldn’t verify. Ask them to try the finished app on staging and explicitly approve that version for live use. Keep development on staging until they give that approval.

  6. Launch the approved version

    Only after the user confirms the app is ready, create the live branch from the exact version they approved on staging. Publish the live environment from that branch. Connect it to its own database and sign-in service, apply the tested migrations, and keep fictional staging records out of live. For later releases, show changes on staging and promote the approved version to live.

    Create the user’s live app account and invite them to sign in at the live URL. Ask whether they want a custom address for the live app, such as crm.example.com. If they do, guide them through connecting it one step at a time. Show them the exact DNS record from the hosting service and where to enter it at their domain provider. Update the live sign-in and invitation links, then verify HTTPS and sign-in at the custom address. If they prefer the hosting service’s address, use that.

    Give the user both links, labelled Staging — try changes and Live — real work. Confirm they can sign in to both, verify the live app works, and walk them through their first task.
